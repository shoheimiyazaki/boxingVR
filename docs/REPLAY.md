# 自動記録と完全再現

## 何が起きるか

- **自動記録**: デスクトップ版・VR 版とも、試合を始めると `replays/miniring_<desktop|vr>_<日時>.mrrep` に記録されます。デスクトップ版は `--no-record` で止められます。
- **再生**: `run.cmd replay [ファイル]` で、記録した試合を再生します（巻き戻し・スロー・シーク・自由なカメラ・展開の見えるシークのバー。下の「リプレイを見る」）。デスクトップ版のゲームセレクトから「過去の試合のリプレイ」を選ぶと、同じフォルダーの記録を一覧から再生できます。省略すると最新の記録を使います。VR で記録したものもデスクトップで再生でき、記録したときの時間刻みどおりに進むので同じ速さで見えます。
- **照合**: `run.cmd verify [ファイル]` で、ウィンドウを開かずに最速で再シミュレーションし、記録どおりに再現できたかを報告します。

## リプレイを見る（デスクトップ）

`run.cmd replay [ファイル]`、またはゲームセレクトの「過去の試合のリプレイ」で開く。開くとすぐ等速で再生が始まり、裏で記録を 1 回だけ最後まで再シミュレーションする（**走査**）。走査が済んだ所まで、巻き戻し・スロー・シークが即座にできる。走査は実時間の数倍（測った値: 約 3〜4.5 倍）で進むので、ふつうの再生は追いつかない。シークのバーの明るい部分が走査の済んだ範囲で、パネルの上に「読み込み N%」と出る。

### 仕組み（`games/MiniRing/Replay/ReplayScanner.cs`・`Presentation/ReplayViewerGame.cs`）

- **場面を貯めて引く**: 走査は試合時間の 1/30 秒ごとに描画の材料（剛体・ボクセルの体・粒・HUD・顔の窓・音）を写して `ReplayFrameCache` に置く。再生ヘッド（`ReplayTransport`）の時刻を挟む 2 枚の間を、姿勢を補間して描く（`PoseBlend`・`VoxelSnapshot.Blend`）。試合は 2 度進めない。
- **世界のスナップショットから再シミュレーションしない理由**: Bepu の接触の記憶（warm start の衝撃）・選手・ボット・ボクセルの全状態を写さないとビット単位で同じ続きにならず、それは試合の全部を複製することになる。物理は決定的なので、先頭から 1 回進めて貯めれば、どの時刻へも同じ物を出せる。場面には写した時点の `StateChecksum` を残し、`ReplayScanTests.SeekedFrame_EqualsTheMatchPlayedFromTheStart` が「シークして出る場面 = 先頭から再生した試合のその歩（チェックサムと描画が同じ）」を確かめる。
- **メモリの上限**: 場面は 1 枚およそ 40〜90 KiB（測った値。体の色が変わるたびに写し直す分が多い。写しは場面どうしで共有し、1 回だけ数える）。見積もりが 384 MiB を越えたら 1 枚おきに捨てて間隔を倍にする（捨てた場面の音は次の場面へ移すので失わない: `Decimating_KeepsEverySoundInOrder`）。長い記録は最初から間隔を広げる。補間するので粗くなっても動きは途切れない。
- **音**: 前へ 2 倍速までで進んだ分だけ、その間に鳴った音を鳴らす。巻き戻し・早送り・シークでは鳴らさない。
- **試合を変えない**: 走査は記録の入力を与えるだけ、観測（`MatchHighlights`）は読むだけ。`PhysicsVersion`・`LogicVersion` は変わらない。

### 展開の見えるシークのバー

画面の下のパネル。左から右が試合の全体（ラウンドの区切りは縦線と `R2` などの札）。

| 段 | 中身 |
|---|---|
| 見込み | 観客の見込み p_red（`WinModel`、docs/EXCITEMENT.md §2）。中央より上へ赤、下へ青が有利 |
| 意識・スタミナ・体 | 両者の推移（赤と青の線。体 = 始めのセルに対する残り） |

## なぜ入力だけで全部が再現できるか

試合の動きを決めるものは、次の 3 つしかありません。

| 要素 | 決定的である理由 |
|---|---|
| 物理（Bepu） | 単一スレッドで、同じ入力なら同じ結果になる |
| CPU | 乱数の種で固定している。どのボットか（スタイルの全値）も見出しに残す |
| プレイヤーの入力 | 毎ステップ、両手の目標・移動・向き・握り・頭の位置・胴のひねり・バネ伝達・武器の向きと解放・リセットとして記録する |

そこで記録するのは、見出しの「乱数の種・調整値（`FighterTuning` の JSON）・CPU のボット（名前とスタイルの JSON）」と、毎ステップの「入力と時間刻み」だけです。これで両者の全剛体の動き、ダメージ、部位の状態、勝敗まで、最初から完全に再現できます。

さらに 60 ステップごと（ライブの固定240 Hzでは試合時間0.25秒ごと）に状態のチェックサム（`BoxingGame.StateChecksum`）を記録します。中身は全剛体の位置・姿勢・速度、体の状態、勝敗です。再生時にこれと照合し、**ずれ始めたステップ**を特定できます。

## ファイル形式（`games/MiniRing/Replay/ReplayFile.cs`）

```
"MRRP" | int32 版(7) | int32 種 | string 調整値 JSON | string ホスト | string ビルド版 | int64 作成日時(UTC)
       | string CPU 名 | string CPU のスタイル JSON（legacy なら空）| int32 ボットの仕組みの版 | int32 体の物理の版
       | string 試合条件 JSON（装備・リング・体格・顔・ルールなど）
以降、レコードの並び:
  0x01 Step:     float dt | 移動 xyz | 向き xyz | 左手 xyz, 握り | 右手 xyz, 握り | 頭 xyz | リセット
                | float 胴のひねり | 左右それぞれ: float Spring, bool 解放, bool 向き有無, あれば quaternion xyzw
                | 左右の手形 | 左右の脚目標（有無と値）
                | v7: 青コーナーの入力の有無 | あれば同じ入力形式（リセット欄は false）
  0x02 Checksum: int32 ステップ番号 | uint64 チェックサム
```

- **ビルド版**: 記録時の `AssemblyInformationalVersion`（コミットハッシュ付き）を残します。
- **CPU**: ボットの名前ではなく**スタイルそのもの**を残します。`champion` を調整し直しても、記録した時の相手で再生できます。CPU 欄は v2、体の物理版は v3 で追加しました。
- **試合条件**: v6 は両者の装備・武器・体格・顔・リング・ルールを記録します。v5 以前にはこれらがなく、既定条件以外で記録した試合の再現は保証できません。
  - スタイルの値が同じでも、ボットの判断の仕組み（`BoxerBot.LogicVersion`）が変われば試合は変わります。仕組みの版が今のビルドと違う記録は、黙ってずれる代わりに「別の版で記録された」と報告して読みません。
- **記録できない試合**: 操作元を記録から復元できないカスタムボットの試合は、記録を始める時点で拒みます。v7 はローカル対戦の青コーナーの入力と、観戦モードの赤CPUのスタイルを保存します。
- **書き出しの間隔**: 約 1 秒ごとに書き出します。強制終了やクラッシュでも、最後の完全なレコードまでは読めて、そこまでは再現できます。
- **容量**: 武器の向きを指定しない通常の 1 ステップは 84 バイト（v4 の追加は 16 バイト）。旧60 Hzでは1分あたり約300KB、新しい固定240 Hzではその約4倍です。
- **旧形式**: v3 も、物理と CPU の版が一致すれば読めます。追加されたバネ伝達・胴のひねりは 0、武器の向きは null として読みます。v1/v2 は物理版を持たないため現在の体では再現できず、読み込みを拒否します。

## 注意

- 物理19では骨折後の肉の断面を追跡し、接続の固さと切断を更新します。物理18以前の記録は版不一致として拒否します。音v7の即時発音は表示側の処理で、記録・試合のチェックサムには加えません。

- 再現が保証されるのは**同じビルド**のときだけです。たとえば回避の基本動作の作業で、しゃがむと膝と股が曲がるようにし（体の物理）、ボットの拳が打ち始めの狙いへ向かうようにしました。それより前の記録は、どこかでずれます。コードや調整値の既定値を変えると、古い記録はどこかでずれます。`verify` が「DIVERGED at step N」と報告し、ずれ始めた位置が分かります。
- 記録されるのは試合の入力です。VR の頭や手のトラッキングの生データそのものではなく、人形への指令に変換した後の値です。そのため再生では VR の視点は再現されず、リング全体を外から見る形になります。

## 確かめたこと

`tests/MiniRing.Tests/ReplayTests.cs` で次を確かめています。

- **完全再現**: 20 秒の試合（途中でラウンドのやり直しを含む）が、全チェックサムと最終状態までビット単位で一致する
- **時間刻み**: 新しいライブ記録は1/240秒固定。旧ホストや同期ホストで作った可変刻みの記録も、記録した刻みどおりに完全再現できる
- **改ざんの検出**: 入力を 1 か所変えると、その直後のチェックサムでずれとして検出される
- **途中で切れたファイル**: 書けたところまでは完全に再現できる
- **見出し**: 乱数の種と調整値が正しく保存されている

実機でも確かめました。デスクトップ版で 8 秒遊んだ記録が一致し、強制終了した記録も書き出し済みの 4 秒分が一致しました（どちらも `run.cmd verify`）。

## 日本刀ログの計測と VR の表示

`dotnet test tests/MiniRing.Tests -c Release -m:1 --filter FullyQualifiedName~RecordedKatanaProbe --logger "console;verbosity=detailed"`

既定の入力は `replays/miniring_desktop_20261114_204945.mrrep`。別の日本刀ログは環境変数 `MINIRING_PROFILE_REPLAY` で指定できます。この計測のみ物理27のログを物理28へ入力し、記録のチェックサムと照合します。

VR は物理をワーカーで進め、OpenXR は最後に完成したシーンを現在の頭の姿勢で両目に描きます。物理が間に合わない間は最新の未処理入力を残して、試合時間を遅らせます。起動時に `run.cmd vr --profile-frames` を指定すると、表示設定の Hz、アプリが描画した FPS、フレーム間隔と処理時間の p99、11.11 ms を超えた間隔数、同じシーンを再利用した数を300フレームごとに表示します。

## ライブ入力の適用歩（作業10）

Desktop と VR は表示フレームから独立した単一の物理スレッドで1/240秒ずつ進みます。入力は未処理の単発操作を保持して受け渡し、各歩の開始時に確定した FighterCommand を ReplayRecorder.Step に渡します。Step レコードの0始まりの並び順が、実際に入力を適用した歩番号です。描画側が何回同じ状態を表示しても、この並びやチェックサムは変わりません。音・振動は別の取りこぼさないキューを使い、シーンを差し替えても失われません。

FixedSimulationTests.AppliedStepInputs_RecordAndReplayBitExactly は途中のリセットを含む実スレッド入力を記録し、歩番号・固定刻み・全チェックサムの一致を確かめます。
