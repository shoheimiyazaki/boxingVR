# 自動記録と完全再現

## 何が起きるか

- **自動記録**: デスクトップ版・VR 版とも、起動するだけで試合が `replays/miniring_<desktop|vr>_<日時>.mrrep` に記録されます。デスクトップ版は `--no-record` で止められます。
- **再生**: `run.cmd replay [ファイル]` で、記録した試合を実時間で再生します。省略すると最新の記録を使います。VR で記録したものもデスクトップで再生でき、記録したときの時間刻みどおりに進むので同じ速さで見えます。
- **照合**: `run.cmd verify [ファイル]` で、ウィンドウを開かずに最速で再シミュレーションし、記録どおりに再現できたかを報告します。

## なぜ入力だけで全部が再現できるか

試合の動きを決めるものは、次の 3 つしかありません。

| 要素 | 決定的である理由 |
|---|---|
| 物理（Bepu） | 単一スレッドで、同じ入力なら同じ結果になる |
| CPU | 乱数の種で固定している。どのボットか（スタイルの全値）も見出しに残す |
| プレイヤーの入力 | 毎ステップ、両手の目標・移動・向き・握り・頭の位置・胴のひねり・バネ伝達・武器の向きと解放・リセットとして記録する |

そこで記録するのは、見出しの「乱数の種・調整値（`FighterTuning` の JSON）・CPU のボット（名前とスタイルの JSON）」と、毎ステップの「入力と時間刻み」だけです。これで両者の全剛体の動き、ダメージ、部位の状態、勝敗まで、最初から完全に再現できます。

さらに 1 秒（60 ステップ）ごとに状態のチェックサム（`BoxingGame.StateChecksum`）を記録します。中身は全剛体の位置・姿勢・速度、体の状態、勝敗です。再生時にこれと照合し、**ずれ始めたステップ**を特定できます。

## ファイル形式（`games/MiniRing/Replay/ReplayFile.cs`）

```
"MRRP" | int32 版(6) | int32 種 | string 調整値 JSON | string ホスト | string ビルド版 | int64 作成日時(UTC)
       | string CPU 名 | string CPU のスタイル JSON（legacy なら空）| int32 ボットの仕組みの版 | int32 体の物理の版
       | string 試合条件 JSON（装備・リング・体格・顔・ルールなど）
以降、レコードの並び:
  0x01 Step:     float dt | 移動 xyz | 向き xyz | 左手 xyz, 握り | 右手 xyz, 握り | 頭 xyz | リセット
                | float 胴のひねり | 左右それぞれ: float Spring, bool 解放, bool 向き有無, あれば quaternion xyzw
                | 左右の手形 | 左右の脚目標（有無と値）
  0x02 Checksum: int32 ステップ番号 | uint64 チェックサム
```

- **ビルド版**: 記録時の `AssemblyInformationalVersion`（コミットハッシュ付き）を残します。
- **CPU**: ボットの名前ではなく**スタイルそのもの**を残します。`champion` を調整し直しても、記録した時の相手で再生できます。CPU 欄は v2、体の物理版は v3 で追加しました。
- **試合条件**: v6 は両者の装備・武器・体格・顔・リング・ルールを記録します。v5 以前にはこれらがなく、既定条件以外で記録した試合の再現は保証できません。
  - スタイルの値が同じでも、ボットの判断の仕組み（`BoxerBot.LogicVersion`）が変われば試合は変わります。仕組みの版が今のビルドと違う記録は、黙ってずれる代わりに「別の版で記録された」と報告して読みません。
- **記録できない試合**: ボット同士の試合（ホストの入力が使われていない）と、スタイルの分からない CPU の試合は、記録を始める時点で拒みます。
- **書き出しの間隔**: 約 1 秒ごとに書き出します。強制終了やクラッシュでも、最後の完全なレコードまでは読めて、そこまでは再現できます。
- **容量**: 武器の向きを指定しない通常の 1 ステップは 84 バイト（v4 の追加は 16 バイト）。60Hz で 1 分あたり約 300KB になります。
- **旧形式**: v3 も、物理と CPU の版が一致すれば読めます。追加されたバネ伝達・胴のひねりは 0、武器の向きは null として読みます。v1/v2 は物理版を持たないため現在の体では再現できず、読み込みを拒否します。

## 注意

- 物理19では骨折後の肉の断面を追跡し、接続の固さと切断を更新します。物理18以前の記録は版不一致として拒否します。音v7の即時発音は表示側の処理で、記録・試合のチェックサムには加えません。

- 再現が保証されるのは**同じビルド**のときだけです。たとえば回避の基本動作の作業で、しゃがむと膝と股が曲がるようにし（体の物理）、ボットの拳が打ち始めの狙いへ向かうようにしました。それより前の記録は、どこかでずれます。コードや調整値の既定値を変えると、古い記録はどこかでずれます。`verify` が「DIVERGED at step N」と報告し、ずれ始めた位置が分かります。
- 記録されるのは試合の入力です。VR の頭や手のトラッキングの生データそのものではなく、人形への指令に変換した後の値です。そのため再生では VR の視点は再現されず、リング全体を外から見る形になります。

## 確かめたこと

`tests/MiniRing.Tests/ReplayTests.cs` で次を確かめています。

- **完全再現**: 20 秒の試合（途中でラウンドのやり直しを含む）が、全チェックサムと最終状態までビット単位で一致する
- **可変の時間刻み**: VR のように毎フレーム時間刻みが変わる記録も、同じく完全に再現できる
- **改ざんの検出**: 入力を 1 か所変えると、その直後のチェックサムでずれとして検出される
- **途中で切れたファイル**: 書けたところまでは完全に再現できる
- **見出し**: 乱数の種と調整値が正しく保存されている

実機でも確かめました。デスクトップ版で 8 秒遊んだ記録が一致し、強制終了した記録も書き出し済みの 4 秒分が一致しました（どちらも `run.cmd verify`）。
