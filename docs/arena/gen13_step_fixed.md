# 240 Hz の 1 歩の決まった費用と割り当てを減らす（作業 13、2026-11-15）

結果（チェックサム）を変えない最適化だけを入れた。刻みは 240 Hz のまま、物理の中の並列化なし。
物差し: `tests/MiniRing.Tests/KatanaStepCostProbe.cs`（Probe。通常の実行から外れる）。
`dotnet test tests/MiniRing.Tests -c Release --filter "FullyQualifiedName~KatanaStepCostProbe"`
環境変数: `STEPCOST_MODE=fist`（拳の試合: champion 対 swarmer、`SimplifyProbe` と同じ）、`STEPCOST_ALLOC=1`（枠ごとの割り当ても数える。時間の表とは別の走りで使う: GC の読みを足すので少し重い）、`STEPCOST_STEPS`（1 シードの歩数、既定 2400）、`STEPCOST_OUT`・`STEPCOST_LABEL`。
計測を切った別の走りと入れて、最終チェックサムが一致することをテスト内で確かめている。

- 5 シード（0〜4）× 2400 歩（240 Hz の 1 歩ずつ）。刀の試合は日本刀・両手持ち・`SwordBot.Basic` 同士。拳の試合は champion 対 swarmer（既定のグローブ）。
- 「触れた」= その歩に `VoxelContact.Resolve` が相手の格子に当たった接触を 1 つ以上返した歩。
- 時間は 1 歩（`game.Step(1/240)`）の CPU 時間 [ms]。Release ビルド。別の作業が同じ機で動いていたので、同じ版の測り直しで ±5〜10 %（最大は GC・JIT の 1 歩が入るので 10〜30 % ゆれる。拳の「後」の最大は 9.3 と 12.4）。
- 割り当ては `GC.GetAllocatedBytesForCurrentThread` の 1 歩の差 [byte]。

## 原因と直した所（すべてビット単位で同じ結果）

1. **`BoxingGame.FullReachOf`（Control の 0.55 ms の正体）**: `_fullReach.GetValueOrDefault(weapon, FarEdge(weapon))` は、既定値の引数 `FarEdge` を毎回先に評価する。`FarEdge` は刀の格子の全セル（10 万超）を割り算で座標に戻しながら歩くので、`ArmedSense`（ボットの判断 2 回）と `UpdatePerception`（2 回）で 1 歩に 4 回、約 0.58 ms（`RawArmedSense` の武器の部分）。`TryGetValue` に変えて、無いときだけ `FarEdge` を求める。Perception 0.28 → 0.005 ms、BotRead 0.27 → 0.005 ms、触れなかった歩の中央値 1.08 → 0.53 ms（この修正だけで。割り当ては変わらない: 計算の重複で、割り当ては 3 の使い回しで減った）。
2. **`BoxingGame.FarEdge`**: 端の値はセルの x だけで決まり x が大きいほど小さくならないので、先の x のスライスから見て最初に埋まったセルで止める（全セルの歩きをやめる）。武器の格子の版が変わった歩（折れ・削れ）の最大が 15 → 11 ms 台に。
3. **`VoxelContact.Sweep.Candidates`**: 毎 Sweep 作っていた「当たるセルのビット列」（刀で 13 KB）をスレッドごとに使い回し（使う語数だけ消す）、4 つの姿勢の配列をやめて局所変数に。候補セルの配列（索引・中心）と、チャンク・まとめの配列（`BuildChunks` 2 回分）もスレッドごとの使い回しにして、使う数（`_cellCount`・`_chunkCount`・`_superCount`）を持つ（Sweep は 1 つ終わってから次が始まる。配列の長さではなく数で回す）。拳の触れた歩の割り当て 188 KB → 36 KB、刀の触れた歩 184 KB → 73 KB。
4. **`VoxelGrid.Split`・`OccupiedBounds`**: 折れ・切断で使う全セルの歩きを、動くスライスだけ・割り算なしの 3 重ループに（セルの順序は元と同じ。`OccupiedBounds` の min/max は順序に依らない）。`SnapSplit` の 1 歩 3.1 ms → 0.5〜0.6 ms。
5. **`BoxingGame.Weapons`**: `WeaponOf`・`GloveOf`（LINQ のクロージャと列挙子の割り当て、毎歩何度も）をループに、`RememberBeforeStepCore` の `Fighters.Any(f => Hands.Any(...))`・`VoxelPartsOf` を直接のループに、`ResolveWeaponsCore` の `_weapons.ToList()`・毎武器の `new HashSet`・`ResolveBodies` の `VoxelPartsOf(...).ToList()` を使い回しの置き場（再入しない）に。
6. **計測の枠の追加**（`StepProfile`）: Perception・BotRead・DriveFighter・ApplyControl・FighterStamina・FighterStanding・FighterDown・ControlTail、ボクサーの `Read` の内側（BotPerceive・BotRead2・BotChoose・BotExecute）、枠ごとの割り当て（`TrackAllocations`）。計測を切っている間は時計も GC も読まない。

## いま残っている費用（刀、触れなかった歩の中央値 0.48 ms）

Bepu 0.10〜0.13（範囲外）、Weapons 0.40〜0.43（候補セルの絞り込み 0.20 と RunScan 0.13 が大半）、Control 0.04、Fighter 0.03。
候補セルの絞り込みは 1 歩に非 Far の Sweep が約 12 本（Far の約 12 本は早く終わる）、1 本あたり約 600 セルを 4 姿勢で変換する計算そのもの（`Vector3.Transform` は手書きの式とビットが合わないので式は変えない: 作業 11）。

## 入れなかった案

- **体のセルの「占有箱」でスキャンの範囲を絞る**（相手の部位の、埋まったセルだけを囲む箱で、最初の接触までの走査の球テストを絞る）: 結果は同じだったが RunScan 0.131 → 0.120 ms（8 %）。コードの複雑さに見合わないので戻した。
- **候補セルの「箱の中に丸ごと入るブリックは各セルのテストを飛ばす」**: 通る候補は全体の 73 % あるが、`_reachLo/_reachHi`（高さ場の範囲）がセルごとの箱の最小・最大から決まるので、飛ばすと結果が変わりうる（遅らせて求める案は、箱の中に丸ごと入るブリックが少なく効かない見込みで入れていない）。
- **重い歩（刀、最大 10〜13 ms）の RunScan（3〜6 ms）を時間方向にまとめて飛ばす**: 作業 11 で効かなかったと記録済み（候補が定義上いつも相手の箱の近くにある）。重い歩の標本の大半は「刃が相手の部位の箱の中を通っている」標本で、チャンクの球テストを通り、セルごとの変換が要る。直すには掃く標本の粗さか候補の定義を変えるしかなく、結果が変わる。
- **`RawArmedSense` を 1 歩 1 回にまとめる**（`UpdatePerception` の結果を `ArmedSense` に使い回す）: `FullReachOf` を直したあと、`RawArmedSense` 全体で 0.005 ms なので不要になった。
- **折れた時の破片の生成（`SplitAt`）の割り当て**: `VoxelGrid.Split` の新しい格子（配列 4 本）は破片の体が持つので避けられない。全セルの歩きをやめたぶんで時間は 3.1 → 0.5 ms まで下がった。
- **`Fighter` 側のスタミナ・足の運び・サーボ・PD**: 0.035 ms/歩で全体の 7 % 以下。測ったが、割り当ても 150 B ほどで、削る所がない。
- ボットの判断を 60 Hz に間引く案は指示書どおり入れていない。
